## 01 / Information baseline

# Controls before production.

Create a traceable coordination layer that helps discipline leads review, assign and close production issues earlier.

### Required inputs

- Current discipline models
- Approved coordinates and federation protocol
- Clash rules and tolerances
- Responsibility and issue-approval matrix

### Naming and controls

- Discipline/model naming, coordinates, levels and federation origin
- Issue identifier, location, system, priority, owner and due-date fields
- Model version, review run and issue-status conventions
- Named discipline lead for every decision-bearing issue

### Standards and constraints

- Client-issued clash rules, tolerances, exclusions and priority classes govern checks
- Automated intersections are rationalized before issue routing
- Axys3D records and supports actions but does not decide engineering resolution
- Only client-authorized model revisions are re-tested as proposed closures

### Verified software and formats

- Revit and IFC discipline models where issued as approved inputs
- NWC/NWD packages for agreed federation workflows
- BCF packages or project-agreed issue registers
- PDF coordination views and reports where required for review

## 02 / Scope and gates

# Production stays reviewable.

Axys3D progresses work against named inputs. Design-bearing decisions and approvals remain client-led.

### Technical scope

- Model federation and alignment checks
- Rule-based clash-review support
- Issue grouping, ownership and status tracking
- Coordination views and meeting outputs

### 01 — Validate model versions and coordinates

**Review gate:** Federation gate: versions, coordinates and model coverage accepted.

### 02 — Federate approved discipline packages

**Review gate:** Rules gate: test set, tolerances, exclusions and priority accepted.

### 03 — Run agreed checks and rationalize findings

**Review gate:** Issue gate: discipline ownership and required response confirmed.

### 04 — Issue items to responsible discipline leads

**Review gate:** Closure gate: authorized discipline lead approves the resolution instruction.

### 05 — Track client-approved closures and re-test

**Review gate:** Handoff gate: open, closed and deferred status acknowledged.

## 03 / Delivery definition

# Acceptance is part of handoff.

### Deliverables

- Federated review model
- Coordination views
- Issue register or BCF package
- Status and handoff report

### Acceptance criteria

- Federation uses the named model versions and agreed coordinate basis
- Every routed item carries traceable evidence, ownership and status
- Re-tested closures reference an approved source-model revision
- Client discipline leads accept the reported coordination status

### Structured handoff

- Versioned federation package
- Open/closed issue record
- Decision and assumption log
- Client-accepted coordination status

### Evidence required

- Written scope approval
- Current source-information register
- Named client approvers
- Approved publication evidence

## Responsibility boundary

No licensed engineering design, clash-resolution authority, code certification or professional sign-off is claimed.

Axys3D provides production, modeling, coordination or delivery support as scoped. It does not act as architect or engineer of record and does not provide statutory sign-off.

### Technical FAQ

# Scope questions, answered precisely.

### Do you resolve clashes?

We support identification, routing, model updates against approved instructions and re-testing. Resolution authority remains with client-authorized discipline leads.

### Which formats can be federated?

Typical workflows use Revit, IFC, NWC/NWD and BCF, confirmed per project.

### Is this licensed MEP design?

No. The service is coordination and production support, not licensed engineering design.

### What qualifies an issue as closed?

An authorized discipline lead approves the resolution instruction, the correct source-model revision is re-tested and the client accepts the recorded status.
